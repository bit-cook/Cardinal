多 Agent 舰队部署手册

用最短路径先打通「微信 → 控制面 → 一台主机上的 Agent」，确认双向收发正常，再按阶段 00–10 做完整部署。每个阶段包含目标、可复制的命令/配置、验收标准。

快速开始00 变量约定01 组网02 框架安装03 控制面04 OpenClaw 接入05 Hermes Sidecar06 微信入口07 命令路由08 安全加固09 端到端验收10 排查与回滚附录

Quick Start

快速开始：5 步跑通最小链路

  1. 组网：所有主机安装 Tailscale 并登录，确认能互相 ping 通（详见阶段 01）
  2. 装一个 Agent：在主机 A 装好 OpenClaw 并启动，确认本机控制台可访问（阶段 02）
  3. 起控制面：Docker 启动 Mission-Control，仅监听 Tailscale 网卡（阶段 03）
  4. 接入口：部署命令路由与入口适配（OpenClaw 插件 / Telegram），配好白名单 allowFrom（阶段 06、07）
  5. 验证：微信（或 Telegram）发送 /list 看到 Agent 在线，发送 /ping 收到回复，即跑通

快速通过标准

  • 微信 /list 能列出至少 1 个在线 Agent
  • 微信 /ping 收到控制面回复，延迟正常
  • 控制面端口不暴露公网，仅 Tailscale 可达

Phase 01

Tailscale 组网

目标：让所有主机在同一加密内网里互相可达，后续管理流量全部走内网，主机不向公网开放端口。

1.1每台主机安装并登录

bash · 所有主机执行
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --hostname=按0.1规划的主机名 --ssh
# 打开输出的授权 URL，用同一 Tailscale 账号登录

1.2开启 MagicDNS 与固定主机名

在 Tailscale 管理后台 DNS 页面启用 MagicDNS；之后可直接用 mc-console、node-openclaw 这类主机名互访，无需记 IP。

1.3连通性测试（在主控机上）

bash · 主控机
tailscale status
ping -c 2 node-openclaw
ping -c 2 node-hermes
  • tailscale status 能看到全部主机且无离线节点
  • 主控机 ping 通每台节点主机名，延迟正常

Phase 02

安装 OpenClaw 与 Hermes 本体

目标：在对应主机上把两个框架装好并以系统服务常驻，重启后自动拉起。

2.1主机 A：安装 OpenClaw

bash · node-openclaw
curl -fsSL --proto '=https' --tlsv1.2 https://openclaw.ai/install.sh | bash
openclaw onboard          # 按向导完成初始化与模型配置
openclaw gateway start

源码方式：git clone https://github.com/openclaw/openclaw.git，随后 pnpm install && pnpm build && pnpm ui:build。

2.2主机 B：安装 Hermes Agent

bash · node-hermes
curl -fsSL https://raw.githubusercontent.com/NousResearch/hermes-agent/main/scripts/install.sh | bash
hermes setup              # 配置模型 Provider 与工作目录
hermes gateway status

2.3配置 systemd 常驻（两台分别执行）

  • 各自 CLI 可正常对话，OpenClaw 控制台默认 http://127.0.0.1:18789

Phase 03

部署 Mission-Control 控制面（枢机自研）

目标：在主控机跑起控制面，数据持久化到 SQLite，仅通过 Tailscale 内网或回环访问。 控制面与命令路由同仓库（bit-cook/shuji 的 packages/mission-control）， Node 仅标准库 + node:sqlite，需要 Node 22.5+（推荐 24，24 起无需实验 flag）。

3.1生成 API Key 与环境文件

bash
cd ~/shuji
openssl rand -hex 24   # 生成 API Key，记下备用：命令路由与心跳 Sidecar 都用它
cp deploy/env/mission-control.env.example deploy/env/mission-control.env
chmod 600 deploy/env/mission-control.env
$EDITOR deploy/env/mission-control.env    # 填入 MC_API_KEY；跨主机才改 MC_HOST

deploy/env/*.env 已被 gitignore（含密钥），只有 *.env.example 入库。

3.2启动前自检（不监听，只验证配置）

bash
set -a; . deploy/env/mission-control.env; set +a
node packages/mission-control/src/cli.js --check
# [ok] 配置合法：127.0.0.1:3000 db=...
# [ok] 数据库与审计目录可写

缺 MC_API_KEY 时 --check 返回退出码 2——控制面无鉴权等于把全部 Agent 交给同主机任何账号，这是红线，不做默认放行。

3.3两种运行形态

bash · 形态 A：跟随本机用户 systemd 会话

for u in mission-control wechat-bridge hermes-sidecar; do
  cp deploy/systemd-user/$u.service ~/.config/systemd/user/cardinal-$u.service
done
systemctl --user enable --now cardinal-mission-control
systemctl --user status cardinal-mission-control
bash · 形态 B：Docker Compose
cd deploy
docker compose up -d mission-control
docker compose logs -f --tail=50 mission-control

3.4验收

  • curl -s localhost:3000/healthz 返回 {"status":"ok"}（探针免鉴权）
  • curl -s localhost:3000/api/agents 返回 401；带 Authorization: Bearer <MC_API_KEY> 返回 []
  • ss -tlnp | grep 3000 只出现 127.0.0.1 或 Tailscale 地址，没有 0.0.0.0
  • 重启控制面后数据库里的 Agent 与任务都还在（WAL 模式，单文件持久）
红线：控制面默认拒绑 0.0.0.0 / ::，需显式 ALLOW_PUBLIC_BIND=1 才放行。 审计默认写 audit.jsonl（0600 + 10MB 轮转 + logrotate 兜底），且只记元数据（方法 / 路径 / 状态 / 耗时 / IP）， 不记请求体——任务标题里可能有机密。

Phase 04

OpenClaw 原生接入

目标：利用原生适配器把主机 A 的 OpenClaw 注册进管理面，心跳与任务自动上报。

4.1面板注册适配器

在管理面 Agents 页面选择框架类型 OpenClaw，填写连接信息；管理面通过读取 OpenClaw 状态目录获取会话与任务，状态目录必须使用绝对路径。

bash · node-openclaw 确认状态目录
echo $OPENCLAW_STATE_DIR
ls -la "$OPENCLAW_STATE_DIR"
# 若为空或相对路径，写入 service 环境文件并设为绝对路径，例如：
export OPENCLAW_STATE_DIR="$HOME/.openclaw/state"

4.2放行管理面回调

bash · node-openclaw
# 主机防火墙仅允许主控机 Tailscale 地址访问网关端口
sudo ufw allow from 100.x.x.10 to any port 18789 proto tcp
sudo ufw reload
  • 面板 Agents 列表出现该 OpenClaw，心跳为在线，模型与工作区信息正确
  • 在 OpenClaw 执行一次任务后，面板任务历史出现对应记录

排错

注册后立即显示离线，多半是状态目录用了相对路径或目录权限不对；改为绝对路径并确认网关进程有读写权限后重启服务。

Phase 05

Hermes 心跳 Sidecar 接入

目标：Hermes 暂无原生适配器，用一个仅依赖标准库的 Python Sidecar，周期性采集 Hermes 状态并按 generic 协议向管理面发心跳。

5.1Sidecar 脚本

正式实现（重试退避、结构化日志、systemd 加固单元、unittest）已入库 github.com/bit-cook/shuji → packages/hermes-sidecar；下方为核心逻辑示意，部署时以仓库版本为准。

python · /opt/hermes-sidecar/sidecar.py
#!/usr/bin/env python3
"""Hermes -> Mission-Control generic 心跳上报，仅用标准库。"""
import json, os, subprocess, time, urllib.request, urllib.error

MC_BASE = os.environ["MC_BASE"]            # http://mc-console:3000
MC_API_KEY = os.environ["MC_API_KEY"]
AGENT_ID = os.environ.get("AGENT_ID", "hermes-node-b")
HERMES_RPC = os.environ.get("HERMES_RPC", "http://127.0.0.1:8765/status")
INTERVAL = int(os.environ.get("INTERVAL", "300"))   # 5 分钟

def fetch_hermes():
    try:
        with urllib.request.urlopen(HERMES_RPC, timeout=10) as r:
            data = json.loads(r.read().decode())
        return "online", data
    except Exception:
        # RPC 不可用时退化为检查 systemd 服务状态
        out = subprocess.run(["systemctl", "is-active", "agent-gateway"],
                             capture_output=True, text=True)
        return ("online" if out.stdout.strip() == "active" else "offline"), {}

def heartbeat():
    status, extra = fetch_hermes()
    body = {
        "framework": "generic",
        "action": "heartbeat",
        "payload": {
            "agentId": AGENT_ID,
            "status": status,
            "reportedAt": int(time.time()),
            "detail": extra,
        },
    }
    req = urllib.request.Request(
        MC_BASE + "/api/agents/heartbeat",
        data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json",
                 "Authorization": "Bearer " + MC_API_KEY},
        method="POST")
    try:
        with urllib.request.urlopen(req, timeout=10) as r:
            print("heartbeat ok:", r.status)
    except urllib.error.URLError as e:
        print("heartbeat failed:", e)

if __name__ == "__main__":
    while True:
        heartbeat()
        time.sleep(INTERVAL)

Phase 07

命令路由

目标：把微信 / Telegram 文本命令翻译成管理面 REST 调用，并把结果格式化回推；核心逻辑平台无关，各入口只是适配器不同。正式实现已入库 github.com/bit-cook/shuji → packages/wechat-bridge（含白名单、二次确认、审计、企业微信加解密、Telegram 长轮询），本页保留核心逻辑示意。

7.1命令协议（微信 / Telegram 直接发送文本）

命令含义管理面动作

7.2路由服务完整脚本（纯 Node，无第三方依赖）

正式实现（企业微信回调加解密、白名单、危险命令二次确认、JSONL 审计、node:test 单测）已入库 github.com/bit-cook/shuji → packages/wechat-bridge；下方为核心逻辑示意，部署时以仓库版本为准。

javascript · /opt/wechat-bridge/bridge.js
#!/usr/bin/env node
// 平台无关的命令处理核心；入口适配见文件末尾说明。
const http = require("http");

const MC_BASE = process.env.MC_BASE;                 // http://mc-console:3000
const MC_API_KEY = process.env.MC_API_KEY;
const ALLOW_FROM = (process.env.WECHAT_ALLOW_FROM || "").split(",").map(s => s.trim());

function mcRequest(path, method = "GET", body = null) {
  return new Promise((resolve, reject) => {
    const url = new URL(MC_BASE + path);
    const data = body ? JSON.stringify(body) : null;
    const req = http.request(url, {
      method,
      headers: {
        "Authorization": "Bearer " + MC_API_KEY,
        "Content-Type": "application/json",
        ...(data ? {"Content-Length": Buffer.byteLength(data)} : {})
      }
    }, res => {
      let chunks = "";
      res.on("data", d => chunks += d);
      res.on("end", () => {
        try { resolve(JSON.parse(chunks)); }
        catch { resolve(chunks); }
      });
    });
    req.on("error", reject);
    if (data) req.write(data);
    req.end();
  });
}

async function handleCommand(text, fromUser) {
  if (!ALLOW_FROM.includes(fromUser)) return "拒绝访问：不在白名单内";
  const parts = text.trim().split(/\s+/);
  const cmd = parts[0];
  try {
    switch (cmd) {
      case "/ping":
        return "pong · " + new Date().toISOString();
      case "/list": {
        const agents = await mcRequest("/api/agents");
        return (Array.isArray(agents) ? agents : agents.data || [])
          .map(a => `${a.agentId || a.id} [${a.status}] ${a.model || ""}`).join("\n");
      }
      case "/status":
        return JSON.stringify(await mcRequest(`/api/agents/${parts[1]}`), null, 2);
      case "/tasks":
        return JSON.stringify(await mcRequest(`/api/agents/${parts[1]}/tasks`), null, 2);
      case "/cost":
        return JSON.stringify(await mcRequest("/api/costs/summary"), null, 2);
      case "/dispatch": {
        const [, agentId, ...taskParts] = parts;
        const task = {agentId, title: taskParts.join(" "), createdAt: Date.now()};
        const r = await mcRequest("/api/tasks", "POST", task);
        return "已下发：" + JSON.stringify(r);
      }
      default:
        return "未知命令。支持：/ping /list /status /tasks /cost /dispatch";
    }
  } catch (e) {
    return "处理失败：" + e.message;
  }
}

// 入口适配（正式实现见 github.com/bit-cook/shuji）：
// 微信（OpenClaw ClawBot）-> cardinal-bridge 插件挂 before_agent_reply 钩子，
//   命中命令即 POST 到桥的 /openclaw 端点，回复经微信通道返回；
// Telegram -> 桥内置长轮询适配器（getUpdates/sendMessage），无需公网地址；
// 企业微信 -> 桥内置回调适配器（验签加解密），主动推送用应用消息接口。
module.exports = {handleCommand};

长轮询只从内网出站连接 api.telegram.org，不监听任何端口、无需公网地址与回调，契合「不暴露公网」红线。Docker 部署用 deploy/docker-compose.yml 里的 wechat-bridge-telegram 服务。

  • 微信（或 Telegram）发送 /ping 收到 pong；非白名单用户发消息被拒
  • /list 能返回两个框架全部实例的在线状态
  • /dispatch 下发后，目标 Agent 面板出现对应任务

Phase 08

安全加固

目标：在正式使用前逐项关闭默认风险，所有条目可独立验证。

  • 管理面默认密码与 API Key 全部更换为强随机值，不复用安装器生成值
  • 管理面与微信桥端口仅绑定 Tailscale 网卡或 127.0.0.1，公网不可达
  • 设置 MC_ALLOWED_HOSTS 白名单，防止 Host 头伪造
  • 微信命令白名单只保留本人 ID，危险操作（dispatch/restart）加二次确认
  • 各主机防火墙默认拒绝入站，仅放行 Tailscale 与明确授权的内网来源
  • Sidecar 与 Bridge 使用最小权限专用账号运行，禁止 root 常驻
  • 密钥统一放 EnvironmentFile 并收紧权限（chmod 600），不入库不入镜像
  • 开启管理面审计日志，定期核对 MCP 调用与注入尝试记录
  • 主机开启自动安全更新，Tailscale 与各组件保持在受支持版本

Phase 10

故障排查与回滚

目标：常见问题按表定位；需要撤销时按回滚顺序操作，数据先备份再拆除。

10.1故障排查表

现象可能原因处理
Agent 持续显示离线心跳未到达：网络不通或服务未运行查 sidecar 日志、ping 主控机、确认 systemd 状态
Hermes 明明在跑，Sidecar 却报 offlineHermes 是用户级 systemd 单元（~/.config/systemd/user/）。在 root 下不带 --user 查 systemctl is-active hermes-gateway.service 会返回退出码 3「没有这个单元」，Sidecar 于是判离线环境文件设 SYSTEMD_UNIT=hermes-gateway.service 与 SYSTEMD_SCOPE=user（或留 auto：遇「无此单元」自动改查 --user）；确认命令 systemctl --user is-active hermes-gateway.service
刚心跳成功，/list 却立刻显示离线心跳报文 reportedAt 是秒（int(time.time())），控制面却拿它和 Date.now()（毫秒）比大小，差值天文数字 → 永远判超时升级到 v0.4+：控制面按量级把秒换算成毫秒。自查：curl /api/agents/<id> 看 lastSeenAt 是否是 13 位毫秒
Agent 显示在线但实际早已停机面板直接采用 Agent 最后自报的状态，没有超时纠偏控制面 MC_STALE_SEC（默认 900）内无新心跳即报 offline，并附 reportedStatus 与 stale: true；按心跳周期调整该值
服务反复重启停不下来StartLimitIntervalSec / StartLimitBurst 写在了 [Service] 段——这两个键属于 [Unit]，写错位置会被静默忽略，重启上限一直是空转v0.4+ 六个单元文件已移到 [Unit] 段；自查 systemd-analyze verify <unit> 应无 Unknown key 告警
心跳返回 401/403API Key 不一致或无权限核对 EnvironmentFile 与管理面 Key；Sidecar 会以退出码 4 结束，systemctl status hermes-sidecar 可见 failed
命令全部返回「拒绝访问」白名单里的 ID 与通道实际 ID 不一致看审计日志里的 from 字段，把它加进 WECHAT_ALLOW_FROM / TELEGRAM_ALLOW_FROM
插件调 /openclaw 返回 401桥配了 BRIDGE_TOKEN 而插件 cardinalToken 没填或不同值两边填同一个值后重载插件
微信发消息无回应回调失效/可信 IP 未配/白名单不匹配检查企微回调与可信 IP、桥服务日志、用户 ID
OpenClaw 微信通道无响应clawbot 插件未装/扫码过期/cardinal-bridge 未注册钩子openclaw channels status --probe；重新扫码；openclaw plugins inspect cardinal-bridge --runtime --json
任务下发失败agentId 错误或目标网关离线先 /list 确认 ID 与在线状态再下发
成本数据为空适配器未上报用量确认状态目录绝对路径，重启对应网关
