Section 01

一句话定位

定位

枢机（Cardinal）是个人 Agent 世界的控制面。把散落在多台主机、异构框架（OpenClaw / Hermes / 任意 CLI）上的 Agent 收进一个控制点：你在微信或 Telegram 发一条文本命令，命令沿「入口 → 网关 → 控制面 → 节点」四层架构下行到具体主机执行；Agent 的状态、心跳、任务与成本数据沿原路上行汇入一个面板。万事，系于此枢。

它不是又一个 Agent 框架，而是框架之上的一层：统一纳管、统一命令、统一审计。项目代号 Agenos（Agent + OS），控制面品牌 Cardinal——中文「枢机」（户枢 + 弩机）与拉丁语 cardo（门轴）是词源上的双胞胎：门轴 → 关键 → 枢机 ＝ Cardinal。

Section 02

解决什么问题

当你拥有不止一台主机、不止一种 Agent 框架时，会出现三个「散」：实例散（这台机器跑着 OpenClaw，那台跑着 Hermes）、入口散（每个框架一个控制台）、账目散（Token 花在哪、任务跑到哪，没有一处看得全。枢机把三个「散」收成三个「一切」：

#原则含义
01一切汇于此多主机、异构框架统一注册：OpenClaw 原生接入，Hermes 经心跳 Sidecar 上报，其他 CLI 走 generic。注册、心跳、任务、成本、审计，一个面板。
02一切令由此出微信 / Telegram 发一条文本 → 命令路由归一 → 控制面 REST → 节点执行。危险命令二次确认后才放行。
03一切只为你唯一管理员，唯一主宰。命令入口白名单只接受你本人；其他人发任何消息，一律拒绝并留痕。

立项时做过全网调研：没有任何单一现成工具同时满足「异构框架 × 跨主机 × 微信双向」三个条件，所以才有了这套组合架构——控制面用开源的 Mission-Control，入口与命令路由自研（本仓库），组网用 Tailscale。

Section 04

两条入口链路（ plus 一条备选）

命令入口是整套系统唯一暴露给人的部分，因此设计原则是：链路最短、认证最硬、不留公网端口。三条链路并行独立，按需启用。

A微信：OpenClaw ClawBot 中转（主线）

步发生什么关键点
1微信发消息给 ClawBot（腾讯 2026 年官方 Bot 通道，底层协议 iLink）官方通道，非协议破解；仅支持私聊
2OpenClaw 主机上的 @tencent-weixin/openclaw-weixin 插件收下消息扫码绑定，会话在 OpenClaw 侧
3枢机的 cardinal-bridge 插件挂 before_agent_reply 钩子拦下这条消息命中命令就不调模型，确定性执行
4插件把 {from: 微信用户ID, text: 命令} POST 到枢机桥的 /openclaw 端点内网 HTTP，Bearer 令牌可选
5桥执行命令（白名单终审在枢机侧），把回复文本交回插件，原路返回微信普通对话则放行给 OpenClaw AI 正常应答

为什么命令「不走模型」：命令执行要的是确定、低延迟、可审计——一条 /list 不应该等大模型想一圈。命中命令走钩子直连，普通对话才交给 AI，两者互不干扰。

BTelegram：官方 Bot API 长轮询（直连）

步发生什么关键点
1找 @BotFather 创建机器人拿令牌；找 @userinfobot 查你的数字用户 ID五分钟搞定，无需服务器
2枢机桥以 ADAPTER=telegram 启动，长轮询 getUpdates只从内网出站，不监听任何端口
3文本消息进同一个命令核心：白名单校验 → 执行 → sendMessage 回推与微信链路共用同一套红线逻辑

长轮询天然契合「不暴露公网」红线：没有回调 URL、没有入站端口、没有证书要维护。启动时默认丢弃宕机期间积压的消息，避免对过期命令刷屏。

C备选：企业微信自建应用

需要群聊命令、或公司环境只有企微时，命令路由可切到 ADAPTER=wecom：官方回调验签加解密（WXBizMsgCrypt 等价实现，零依赖）、白名单、主动推送。Gewechat 类个人微信协议方案已停止维护，不再推荐。

Section 05

一条命令的完整旅程

以最典型的危险命令 /dispatch（下发任务）为例——它必须经过二次确认，最能体现红线的存在方式：

你 · 微信 / Telegram

/dispatch node-hermes 夜间巡检一次

枢机 · 命令路由

⚠ 危险操作待确认：/dispatch node-hermes 夜间巡检一次

60 秒内发送 /confirm 3F9A2C1D 执行

发送其他任意消息即取消

你 · 微信 / Telegram

/confirm 3F9A2C1D

枢机 · 命令路由

已下发：{"ok":true,"task":{"id":"task-1","agentId":"node-hermes","title":"夜间巡检一次",…}}

这一进一出之间，命令核心做了七件事：

  1. 白名单校验：发送者 ID 不在 allowFrom 集合，直接回「拒绝访问」并写审计——命令根本不会被解析
  2. 危险识别：/dispatch 命中危险命令表，先生成一次性令牌（8 位十六进制），不调用管理面
  3. 令牌消费：/confirm 校验令牌存在、未过期（60 秒）、且发起人是同一个人；三者任一不满足即拒绝
  4. 执行：通过 Mission-Control 客户端 POST /api/tasks 真正下发，Bearer 鉴权、10 秒超时
  5. 审计：每一步（含被拒绝的）都以 JSONL 追加到审计日志：时间、发送者、命令、结果
  6. 端点鉴权：桥配了 BRIDGE_TOKEN 时，/openclaw 与 /message 无令牌一律 401——插件的 cardinalToken 由此真正生效
  7. 限流：每发送者令牌桶（默认 60 条/分、突发 20），插件重试风暴打不穿控制面；被限流的消息同样留痕
审计日志 · audit.jsonl
{"ts":"2026-11-05T07:30:15.337Z","from":"me","cmd":"/dispatch node-hermes 夜间巡检一次","result":"confirm_required"}
{"ts":"2026-11-05T07:30:22.914Z","from":"me","cmd":"/confirm 3F9A2C1D","confirmed":"/dispatch node-hermes 夜间巡检一次","result":"ok"}

Section 08

心跳 Sidecar：没有原生适配的框架怎么纳管

Mission-Control 原生适配 OpenClaw；Hermes 暂无官方适配，解法是一个仅依赖 Python 标准库的伴生进程：

  1. 采状态：先问 Hermes 本地 RPC（http://127.0.0.1:8765/status）；不可用则退化查 systemd 单元是否 active；两者皆败才报 offline
  2. 上报：按 generic 协议 POST /api/agents/heartbeat，带上 agentId、状态、时间戳和详情，Bearer 鉴权
  3. 重试：失败指数退避（默认 3 次，带抖动）；401/403 以退出码 4 结束——密钥错误重试无益，配合 systemd StartLimit 让单元进入 failed 被看见，而不是无声刷日志
  4. 常驻：systemd 托管，SIGTERM 优雅退出，JSON 结构化日志直接进 journald

效果：Hermes 停机后一个心跳周期内，/list 与面板同步转离线；恢复后自动回线——这正是验收用例 T4 / T5 自动验证的行为。
