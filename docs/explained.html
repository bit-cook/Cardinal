Section 01

一句话定位

定位

枢机（Cardinal）是个人 Agent 世界的控制面。把散落在多台主机、异构框架（OpenClaw / Hermes / 任意 CLI）上的 Agent 收进一个控制点：你在微信或 Telegram 发一条文本命令，命令沿「入口 → 网关 → 控制面 → 节点」四层架构下行到具体主机执行；Agent 的状态、心跳、任务与成本数据沿原路上行汇入一个面板。万事，系于此枢。

它不是又一个 Agent 框架，而是框架之上的一层：统一纳管、统一命令、统一审计。项目代号 Agenos（Agent + OS），控制面品牌 Cardinal——中文「枢机」（户枢 + 弩机）与拉丁语 cardo（门轴）是词源上的双胞胎：门轴 → 关键 → 枢机 ＝ Cardinal。

Section 02

解决什么问题

当你拥有不止一台主机、不止一种 Agent 框架时，会出现三个「散」：实例散（这台机器跑着 OpenClaw，那台跑着 Hermes）、入口散（每个框架一个控制台）、账目散（Token 花在哪、任务跑到哪，没有一处看得全。枢机把三个「散」收成三个「一切」：

#原则含义
01一切汇于此多主机、异构框架统一注册：OpenClaw 原生接入，Hermes 经心跳 Sidecar 上报，其他 CLI 走 generic。注册、心跳、任务、成本、审计，一个面板。
02一切令由此出微信 / Telegram 发一条文本 → 命令路由归一 → 控制面 REST → 节点执行。危险命令二次确认后才放行。
03一切只为你唯一管理员，唯一主宰。命令入口白名单只接受你本人；其他人发任何消息，一律拒绝并留痕。

立项时做过全网调研：没有任何单一现成工具同时满足「异构框架 × 跨主机 × 微信双向」三个条件，所以才有了这套组合架构——控制面用开源的 Mission-Control，入口与命令路由自研（本仓库），组网用 Tailscale。

Section 04

三条入口链路（ plus 一条备选）

命令入口是整套系统唯一暴露给人的部分，因此设计原则是：链路最短、认证最硬、不留公网端口。三条链路并行独立，按需启用。

A微信：枢机原生 iLink 长轮询（主线）

步发生什么关键点
1微信发消息给 ClawBot（腾讯 2026 年官方 Bot 通道，底层协议 iLink：HTTP + 长轮询 + Bearer）官方通道，非协议破解；仅支持私聊
2一次性扫码登录：终端里画出二维码，手机微信扫，服务端签发 bot_token 与 ilink_bot_id只有这一步需要人在场；之后无人值守
3令牌与同步游标落进 WECHAT_STATE_FILE（原子写入，0600）systemd 单元只做长轮询，不再需要交互
4枢机桥以 ADAPTER=weixin 单独起一个进程，长轮询 ilink/bot/getupdates，原样回传服务端游标 get_updates_buf不需要安装 OpenClaw，也不经过任何 Agent 宿主
5文本消息进同一个命令核心：白名单校验 → 执行 → ilink/bot/sendmessage 回推与 Telegram 链路共用同一套红线逻辑

两个必须照做的协议细节，错了都是静默故障：message_id 等 uint64 字段超出 2^53 后 JS number 会丢精度，所以先把它们替换成字符串再解析；get_updates_buf 是服务端同步游标，丢了它服务端会重放积压——表现为把用户下线期间发的命令重新执行一遍。协议实现在 packages/wechat-bridge/src/ilink.js。

BTelegram：官方 Bot API 长轮询（直连）

步发生什么关键点
1找 @BotFather 创建机器人拿令牌；数字用户 ID 可跑 deploy/wait-telegram-sender.sh 让脚本自动认领五分钟搞定，无需服务器
2枢机桥以 ADAPTER=telegram 单独起一个进程（独立 env 文件与 systemd 单元），长轮询 getUpdates只从内网出站，不监听任何端口
3文本消息进同一个命令核心：白名单校验 → 执行 → sendMessage 回推与微信链路共用同一套红线逻辑

长轮询天然契合「不暴露公网」红线：没有回调 URL、没有入站端口、没有证书要维护。启动时默认丢弃宕机期间积压的消息，避免对过期命令刷屏。

一个进程只跑一个适配器。微信入口与 Telegram 入口是两个进程，各有自己的环境文件、 systemd 单元与审计日志——不是同一份配置切个开关。把 ADAPTER=telegram 追加进微信那份 env 文件， 顶掉的是正在服务的微信入口；而白名单取的是两个入口 ID 的并集，配错一边的症状是「服务正常起来了，但每个真实用户都被拒」。

C备选：企业微信自建应用

需要群聊命令、或公司环境只有企微时，命令路由可切到 ADAPTER=wecom：官方回调验签加解密（WXBizMsgCrypt 等价实现，零依赖）、白名单、主动推送。Gewechat 类个人微信协议方案已停止维护，不再推荐。

Section 05

一条命令的完整旅程

以最典型的危险命令 /dispatch（下发任务）为例——它必须经过二次确认，最能体现红线的存在方式：

你 · 微信 / Telegram

/dispatch node-hermes 夜间巡检一次

枢机 · 命令路由

⚠ 危险操作待确认：/dispatch node-hermes 夜间巡检一次

60 秒内发送 /confirm 3F9A2C1D 执行

发送其他任意消息即取消

你 · 微信 / Telegram

/confirm 3F9A2C1D

枢机 · 命令路由

已下发：{"ok":true,"task":{"id":"task-1","agentId":"node-hermes","title":"夜间巡检一次",…}}

这一进一出之间，命令核心做了七件事：

  1. 白名单校验：发送者 ID 不在 allowFrom 集合，直接回「拒绝访问」并写审计——命令根本不会被解析
  2. 危险识别：/dispatch 命中危险命令表，先生成一次性令牌（8 位十六进制），不调用管理面
  3. 令牌消费：/confirm 校验令牌存在、未过期（60 秒）、且发起人是同一个人；三者任一不满足即拒绝
  4. 执行：通过 Mission-Control 客户端 POST /api/tasks 真正下发，Bearer 鉴权、10 秒超时
  5. 审计：每一步（含被拒绝的）都以 JSONL 追加到审计日志：时间、发送者、命令、结果
  6. 端点鉴权：桥配了 BRIDGE_TOKEN 时，/openclaw 与 /message 无令牌一律 401——插件的 cardinalToken 由此真正生效
  7. 限流：每发送者令牌桶（默认 60 条/分、突发 20），插件重试风暴打不穿控制面；被限流的消息同样留痕

红线不是口号，每一条都有对应实现和可独立执行的验证方式：

红线实现怎么验证

危险命令二次确认confirm.js：60 秒 TTL、一次性、仅发起人；未确认不触达管理面单测「先要令牌，确认后才真正下发」「令牌过期」
全量审计audit.js：JSONL 一行一条，含被拒命令cat /var/log/wechat-bridge/audit.jsonl
密钥不入库不入镜像只走环境变量 / EnvironmentFile，模板 deploy/env/*.example，chmod 600git log -p | grep -i secret 无结果
最小权限运行systemd 单元：专用账号 + NoNewPrivileges + ProtectSystem=strict，禁止 root 常驻systemd-analyze verify 单元文件

Section 08

心跳 Sidecar：没有原生适配的框架怎么纳管

Mission-Control 原生适配 OpenClaw；Hermes 暂无官方适配，解法是一个仅依赖 Python 标准库的伴生进程：

  1. 采状态：先问 Hermes 本地 RPC（http://127.0.0.1:8765/status）；不可用则退化查 systemd 单元是否 active；两者皆败才报 offline
  2. 上报：按 generic 协议 POST /api/agents/heartbeat，带上 agentId、状态、时间戳和详情，Bearer 鉴权
  3. 重试：失败指数退避（默认 3 次，带抖动）；401/403 以退出码 4 结束——密钥错误重试无益，配合 systemd StartLimit 让单元进入 failed 被看见，而不是无声刷日志
  4. 常驻：systemd 托管，SIGTERM 优雅退出，JSON 结构化日志直接进 journald

效果：Hermes 停机后一个心跳周期内，/list 与面板同步转离线；恢复后自动回线——这正是验收用例 T4 / T5 自动验证的行为。

单机一切从简四个组件全跑在用户级 systemd 单元里（不占 root、不建系统账号）拷 deploy/systemd-user/*.service 到 ~/.config/systemd/user/；Hermes 与 OpenClaw 本来就是用户级单元时最省事

四个入口适配器是同一份代码的四个进程：ADAPTER=weixin 服务微信（iLink 原生），ADAPTER=telegram 服务 Telegram，ADAPTER=http 服务人工排查，ADAPTER=wecom 服务企业微信——按需启用，互不影响。每个进程有自己独立的环境文件、systemd 单元与审计日志，白名单则是两个入口 ID 的并集（安全，因为只有一个通道的消息能到达给定适配器）。

Section 11

现状与路线

✓已完成（v0.6，CI 全绿，双入口真机联调通过）

  • 命令路由：白名单、八条命令（ping/list/status/tasks/cost/dispatch/confirm/help）、二次确认、审计（0600 + 轮转）、限流、端点 Bearer 鉴权、四个入口适配器
  • 控制面（v0.4 新增，枢机自研）：Agent 注册与心跳、任务下发/领取/回报、Token 成本计量、Bearer 鉴权、审计只记元数据、读路径心跳超时纠偏（不再轻信 Agent 自报的 online）、SQLite 持久
  • OpenClaw 插件（可选项）：message_received 记发送者 + before_agent_reply 拦命令（不走模型）；类型检查对真实 SDK 零错误
  • Hermes 心跳 Sidecar：generic 协议、状态退化（自动识别 system / --user 作用域）、重试退避（带抖动）、401/403 退出码 4、优雅退出
  • 双入口真机联调通过：微信（ClawBot → 枢机桥）与 Telegram（长轮询）都已实跑，各自独立的环境文件、单元与审计日志；Telegram 数字 user_id 由脚本自动认领，不必人工查
  • 部署：compose（read_only / cap_drop / healthcheck）/ systemd 加固（系统作用域 + 用户作用域两套，共 10 个单元）/ logrotate / env 模板 / install.sh（含启动前自检与卸载）；CI 六 job；T1–T26 验收全过
  • 常驻加固（v0.5）：启动即校验配置（配错就起不来，而不是起来后拒绝所有人）；心跳流水与 detail 大小有上限；限流桶与计数器键数有界；审计文件与 SQLite 均 0600；Telegram 入口只接私聊
  • 微信入口改为枢机原生（v0.6）：iLink 协议由枢机自己实现（packages/wechat-bridge/src/ilink.js），扫码登录后令牌落状态文件 0600，之后长轮询无人值守——使用枢机不再需要安装 OpenClaw
  • 网页面板（v0.6）：控制面同一个端口上的只读面板（/panel）。用 MC_API_KEY 换一个 HttpOnly + SameSite=Strict 的会话 Cookie（HMAC 签名、12 小时有效、防篡改、登录按 IP 限流）；只读，写操作仍走命令入口的二次确认，因此不引入 CSRF 面
  • 通道可扩展：入口适配器是注册点——新通讯工具只需一个适配器文件，红线逻辑全在核心里复用
